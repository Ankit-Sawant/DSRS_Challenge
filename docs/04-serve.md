## 4.1 · The model

Your agent is graded against:

| | |
|---|---|
| **Model** | [`google/gemma-4-31B-it`](https://huggingface.co/google/gemma-4-31B-it) |
| **Server** | vLLM, OpenAI-compatible |
| **Temperature** | 0.0, fixed — overriding it has no effect |
| **Max context, max output tokens, tool calling** | as published on the [model card](https://huggingface.co/google/gemma-4-31B-it) — we serve it as-is, at whatever limits Hugging Face lists |
| **Structured output** | supported — see `agents/llm.py` |
| **Network** | egress restricted to the model endpoint |

Check the model card, not this table, for exact context and output-token limits — it is
the source of truth and won't drift out of date the way a copied number here would.

You will not have our endpoint. Develop against your own — anything OpenAI-compatible
works: Ollama, LM Studio, vLLM, llama.cpp. Running a smaller Gemma locally will get you
closer to grading behaviour than a different model family.

**Use `agents/llm.py`.** It reads its configuration from environment variables, so
pointing it at your model is a `.env` change and nothing else:

```bash
cp .env.example .env      # then fill in LLM_BASE_URL and LLM_API_KEY
python -m agents.llm      # confirms the connection works
```

**At grading time we replace your `.env` with ours.** Your agent then runs against our
endpoint with no code change — which is the point of keeping configuration out of the
code. Never commit a `.env` or hard-code a key or URL; `agents/llm.py` is a frozen file
and your edits to it are discarded before grading.

`LLM_MODE=mock` returns deterministic canned responses without contacting anything,
so your tests can run with no model at all.

## 4.2 · The contract

```
python -m agents.answer "which manager held the largest Apple position in 2026 Q2?"
```

stdout, and nothing else on stdout:

```json
{
  "answer": 4182300000,
  "unit": "USD",
  "sources": ["0001423053-26-000012"]
}
```

| Field | |
|---|---|
| `answer` | Scalar or list. Numbers as numbers, not strings. `null` when you cannot answer. |
| `unit` | `USD`, `SHARES`, `COUNT`, `PERCENT`, `NAME`, `DATE`, or `NONE` |
| `sources` | Accession numbers supporting the answer, dashed form |

Logging goes to stderr.

**`sources` is graded separately, and it matters as much as the answer.** A researcher
who cannot trace a number back to a filing cannot use it in a paper. An agent that is
right without knowing why is right by accident.

We run ten held-out questions. Some have a single defensible answer; some do not. **When
the data does not support an answer, return `null` and say so** — that scores better than
a confident guess. Inventing a number is the one failure mode with no upside.

## 4.3 · Secure

Assume the question is hostile, because eventually one will be.

**The data is read-only.** Your agent answers questions; it does not modify anything. If
it generates and executes queries, the connection must be incapable of writing. "Drop the
holdings table" should fail because it cannot succeed, not because a prompt asked the
model nicely.

**Model output is untrusted input.** Anything the model produces — a query, a filename,
a path — is a suggestion from a system that can be talked into things. Validate it before
you act on it. Text generated by an LLM and passed unchecked into an execution context is
the same class of bug as unsanitised user input in a SQL string.

**Filing text is attacker-influenceable.** `name_of_issuer` and `title_of_class` are free
text filed by third parties. If you put them into a prompt, you have put text you do not
control into an instruction channel.

**No credentials in the repository.** Not in code, not in config, not in commit history.

---

## 4.4 · Reliable

**Same question, same answer.** Temperature is zero at grading time. If your agent gives
different answers to identical questions across runs, something in it is non-deterministic
— unordered iteration, a tie-broken sort, a retry that changes the prompt.

**Handle model output that isn't what you expected.** `agents/llm.py` gives you a way to
ask for a specific JSON shape and get it back reliably — use it rather than asking the
model nicely and parsing whatever arrives. It guarantees the shape, not the content: a
well-formed empty answer is still an empty answer.

**Failure returns an answer, not a traceback.** A question your agent cannot handle
should produce `{"answer": null, ...}` with the reason on stderr. A crash scores zero for
that question; an honest null does not.

## 4.5 · Scalable

The dataset is small enough that a slow approach still finishes, which is exactly why
this is worth being deliberate about.

**Do not put the dataset in the prompt.** Thousands of holdings will not fit in context,
and the fact that a two-quarter slice nearly might is a trap. Query the data and put the
result in the prompt, not the other way round.

**Bound the work per question.** An agent that retries until something parses, or walks
every row through the model, works at this size and collapses at ten times it.

We record tokens and requests per question. `agents/llm.py` tracks both — write them out:

```python
from agents.llm import usage
```

### `output/agent_usage.json`

```json
{
  "questions": [
    {"question": "...", "calls": 3, "prompt_tokens": 4210,
     "completion_tokens": 180, "elapsed_seconds": 2.4}
  ],
  "totals": {"calls": 31, "prompt_tokens": 44120, "completion_tokens": 1980}
}
```

Run it over the example questions in `docs/questions-examples.md` and commit the result.

Efficiency is read as a ratio, not a race. Answering ten questions in thirty calls and
answering them in nine hundred are different designs, and the difference shows up long
before it shows up in a bill.

## 4.6 · Maintainable

Someone else has to change this in six months.

**Separate the parts.** Prompt text, data access, orchestration, and output formatting
are four concerns. When they are one function, changing the prompt risks breaking the
query.

**Make it testable without a model.** `LLM_MODE=mock` exists for this. If nothing in your
agent can be tested without a live endpoint, everything in it is coupled to the endpoint.

**Write down what you decided.** Why this retrieval approach, what you tried that failed,
where it breaks. `submission/ASSUMPTIONS.md` is the place.

## How this chapter is graded

| | Points |
|---|---|
| **Answer accuracy** — correct values on ten held-out questions | 5 |
| **Source attribution** — correct accessions, and `null` where the data does not support an answer | 2 |
| **Secure** — read-only access, model output validated before use, no committed credentials | 1 |
| **Reliable** — deterministic, handles unexpected output, fails to an answer rather than a traceback | 1 |
| **Scalable and maintainable** — bounded token and request use, separable components, testable without a model | 1 |

Accuracy and attribution are machine-graded. The rest is read, and asked about in the
walkthrough — where the question is usually "what happens if I ask it this?" rather than
"explain your architecture."
